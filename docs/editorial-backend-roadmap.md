# 创作审核的后端扩展方案与进度

0.1.5 只调整 skills、文档与验证。0.1.6 已实现第 4 项的候选批量重放，发布不自动更新已安装插件；以宿主实际 schema 为准。第 1—3 项仍是未实现方案，不得向现有工具传入提议字段。

## 1. 多章审查绑定

现状：Review 绑定单一章节 source_version/hash；跨章报告只能在 content 中保存版本清单。建议新增独立的范围审查记录，包含已读 manifest、范围、候选结局分组、判定、跨源引文和未读范围。单章 Review 保持兼容。

验收：章A的建立与章B的回应各自校验来源；B改版后范围审查标为需复核，其他书不受影响；缺章不能生成全覆盖状态；候选结局不混算。报告可以有审美分歧，后端只验证覆盖和引用，不自动判文学优劣。

## 2. 条件授权与审查结果

现状：采纳验证 review 与正文绑定，但“存在审查”不等于“无阻碍且独立审查”。建议显式区分人工采纳与有范围、条件和撤销能力的代采纳策略，记录审查结论、未解决发现及执行者来源。

验收：授权要求独立审查时，自审不满足；有未解决阻碍时不自动提交；作者可以明确保留问题或修改授权。执行者身份依宿主可核验信息记录，不能把模型自报当绝对保证。不扩大原有授权，不为人工决定添加额外强制审批。

## 3. 上下文分层

建议保护本场目标、必要硬约束和因果信息的预算，按任务检索相关的叙事期待、人物声音与近期场景变化，再按需展开技术细目。有限视角限制角色知情，不应排除无剧透的风格与作者表达要求。

验收：小预算仍保留关键约束；角色不会收到作者秘密；风格不被大段账目挤空；必要金额/伤情不因“文学优先”丢失。比较检索结果和真实写作输出，不能只看返回字符数。

## 4. 批量修订与统一重放（0.1.6 已实现）

`revision_batch` 在同一基线 manifest 上绑定修订源与审查，从最早变动章顺序暂存全部受影响源的新记忆，全部通过后原子切换指针与记忆。复用现有 jobs/batches，无迁移；候选前缀的证据与依赖验证仍保留。操作与兼容边界见[批量修订协议](../skills/novel/references/batch-revision.md)，实测见[优化验证](optimization-verification.md)。

验收：中途失败无半套正式稿，外部编辑/基线冲突可发现，可恢复重放；只改措辞也不盲复用旧证据偏移；涉及知识变化时重提取受影响后文。内容相同与上下文相同分开验证，不能取消现有版本保护来换取速度。

第 1—3 项仍需单独设计兼容性与事务测试。批量重放不自动实现多章范围审查记录或条件授权的后端执行者认证，也不代替文学终审。
