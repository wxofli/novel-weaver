# 批量修订与统一重放

仅在宿主实际提供 `revision_batch`，且同一批需要修订多个**已采纳章节**时读取。新增章节、设定替换、单章修改沿用原流程。已有授权仍有效；commit 必须有覆盖这些精确版本的作者采纳指示或已满足的条件授权，独立审查由执行者实际完成，后端不自动证明这一条件。

## 候选集与顺序重放

1. 读状态，记录 revision；完成或明确中止已有任务。列出改动章、保留的结局及跨章依赖。在同一正式基线上，逐章 build context、保存新源、读完分页，保存绑定其 `source_version/source_hash` 的审查。审查应同时核对新候选之间的因果，而非只对旧正式稿。暂不逐章采纳或 stage；正文再改必须重建该版本的审查。
2. `revision_batch(mode="prepare",expected_revision=基线,revisions=[{source_version,source_hash,review_id},...],include_source=true)`。所有写请求带共同身份及操作 ID。冻结从最早改动章到末章的候选源序列；未改章使用当时正式源。响应保留 job_id、baseline_revision 和下一源。准备、暂存均不改变正式指针、正式记忆或 revision。
3. 读完响应 `source` 的所有页，按新前缀重新提取该源 delta。每章仍校验哈希、逐字引文和全源字符偏移；未改章也可能因前置事实变化需要新提取。不能把旧 delta 原样重交当作完成核验。
4. `revision_batch(mode="apply",job_id,source_version=下一精确源,delta,include_source=true)`。只允许顺序推进。后端在可回滚候选前缀上验证跨章事实/知情引用，成功后持久化候选进度，再返回下一源，无需额外 next/get 首段。
5. 中断后用 `revision_batch(mode="next",job_id,include_source=true)` 恢复。候选前缀信息不足时用 `mode="context",entity_ids=[相关稳定ID],max_chars=...`：返回截至已暂存位置的作者层事实，最多 50 项，`truncated` 时按实体缩小范围或补读候选证据。它不是角色知情视图，也不包含全部伏笔/实体词典；其他普通查询仍读旧正史。不能用旧正史查询结果覆盖已变更的候选事实。
6. `ready_to_commit=true` 后核实授权条件和最终版本，调用 `revision_batch(mode="commit",job_id,expected_revision=基线)`。事务内再次验证全部版本/审查/上下文与基线，切换全部修订章指针及整段记忆，只增加一次 revision。检查响应状态、投影待办和最终 book_status；`partial` 可能表示数据库已提交但手工文件冲突仍需处理。

## 冲突与退出

保存更新候选、基线冲突或过期审查会阻止继续，不自动换稿、换证据。用 `mode="abort",job_id` 放弃候选任务，正式稿仍旧；修正后重新准备。已成功的同一请求可用完全相同的操作 ID 重试；改变 delta 或参数必须换 ID。事务失败不会留下半套正式指针，重试前先核对状态。

新任务沿用原 jobs/batches 存储，不需要迁移；旧运行时不认识 revision_batch。任务未完成时不要降级或换旧运行时恢复。候选验证内部仍会重建前缀；这里减少的是模型语义提取次数和往返，不承诺数据库只遍历一次。
